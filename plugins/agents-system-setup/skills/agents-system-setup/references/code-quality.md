# Code Quality & Maintainability Standards

Use this reference when the plugin generates an agent system for a
software-development project. The Build Gate (see
[sdlc-build-gate](./sdlc-build-gate.md)) verifies that a change builds, tests,
and reviews cleanly. This reference defines the **authoring standards** the
coding agents follow *while writing the code in the first place*, so the code
that agents generated by this plugin produce is maintainable, conventional, and
review-ready — not just green on CI.

This is the difference between *gate* and *craft*: the Build Gate is verification
at the end; code quality is the standard applied during authoring. The two are
complementary and both reference each other.

> **Code quality** governs the project's source code written or reviewed by
> coding agents. **Content quality** ([content-quality](./content-quality.md))
> governs the prose of the generated agent system itself. They never substitute
> for each other; the output markers are `Code quality:` and `Content quality:`.

This reference is source-backed and original. Do not copy text, checklists, or
prose from any book, style guide, or proprietary product; cite the source family
and express the concept in original words.

## Source-backed model

| Source | Public concept used here |
|---|---|
| Google Engineering Practices — Code Review Developer Guide (`google.github.io/eng-practices/review/`) | What reviewers look for: correctness, readability, simplicity, naming, tested behavior, conformance to project conventions, no needless complexity. |
| Google Style Guides (`google.github.io/styleguide/`) | Language-specific conventions exist and should be followed; a project's own configured style wins over personal preference. |
| ISO/IEC 25010 product-quality model | Maintainability sub-characteristics: modularity, reusability, analysability, modifiability, testability — the qualities to optimize for. |
| Refactoring catalog and code-smell taxonomy (Fowler family) | Named smells (long function, large class, duplicated code, deep nesting, primitive obsession, dead code) signal where to refactor. |
| Clean Code principles (Martin family) | Meaningful names, small single-purpose functions, comments explain *why* not *what*, leave code cleaner than found. Concepts only — never copied text. |
| The Pragmatic Programmer (Hunt & Thomas) | DRY (one authoritative representation of each piece of knowledge) and orthogonality (decoupled, independent modules). |
| McCabe cyclomatic complexity (NIST SP 500-235, structured testing) | Bounded branching per unit keeps code analysable and testable; high complexity is a refactor signal. |
| OWASP Secure Coding Practices | Input validation at boundaries and explicit, non-silent error handling — cross-links to [security-audit-architecture](./security-audit-architecture.md). |

## Rule 0 — Conform to existing conventions first

The single highest-leverage rule. Before writing or changing code, a coding
agent **detects and conforms to the project's established conventions** instead
of importing a personal or generic style:

1. **Read the configured tooling** and obey it: `.editorconfig`, ESLint/Prettier,
   Ruff/Black/isort, `gofmt`/`golangci-lint`, `rustfmt`/Clippy, Checkstyle/
   Spotless, SwiftLint/SwiftFormat, ktlint, PHP-CS-Fixer, RuboCop, and any
   `pre-commit` config present.
2. **Match local patterns**: naming, file/module layout, error-handling style,
   logging, dependency-injection approach, test structure, and public-API shape
   already used in neighbouring files.
3. **Do not introduce a new framework, formatter, lint rule, or architectural
   style** unless the task explicitly calls for it and the plan approves it.
4. **When conventions conflict or are absent**, fall back to the standards below
   and record the assumption; never silently impose a divergent style.

Conforming to an existing convention always beats a "better" convention applied
inconsistently.

## Authoring standards

Compact, language-agnostic standards every coding/implementer agent applies.
Depth and examples live in the generated `code-quality` skill.

- **Naming.** Names reveal intent and are searchable and pronounceable; avoid
  ambiguous abbreviations. Follow the language's casing convention.
- **Functions and units.** One responsibility per function; keep them short and
  shallow. Prefer early returns over deep nesting. Keep cyclomatic complexity
  bounded; extract a helper when branching grows.
- **DRY.** Each piece of knowledge has one authoritative representation. Extract
  repeated logic — but do not over-abstract a single use (avoid speculative
  generality).
- **Simplicity (YAGNI).** Solve the present requirement. Do not add abstractions,
  options, or indirection for hypothetical future needs.
- **Separation of concerns / coupling.** Keep modules orthogonal: a change in one
  should not force changes across many. Depend on stable interfaces.
- **Error handling.** Fail fast and explicitly. Never swallow errors or convert a
  failure into success-shaped output. Surface errors through the project's normal
  mechanism; validate at system boundaries (input, files, network, IPC).
- **Comments and docs.** Comment the non-obvious *why* — a constraint, invariant,
  or workaround. Do not narrate what well-named code already states. Keep public
  APIs documented in the project's doc style.
- **Dead code.** Delete unused code, commented-out blocks, and unreachable
  branches; rely on version control for history. No leftover stubs or scaffolds.
- **Magic values.** Replace unexplained literals with named constants or config.
- **Tests as first-class code.** New behaviour ships with tests; a bug fix ships
  with a regression test. Cover edge and failure paths, not only the happy path.
  Tests are readable and follow the project's existing test style. Never weaken,
  skip, or delete a test merely to make a change pass.
- **Formatting.** Defer entirely to the project's formatter/linter; do not
  hand-format against it or reformat unrelated lines.

## Signal taxonomy (code smells)

The `code-quality-reviewer` (or `@reviewer` when merged) reports any of these on
a change. Each maps to a concrete refactor.

| Signal | Fail mode | Typical fix |
|---|---|---|
| `convention-drift` | Ignores the project's configured linter/formatter or local patterns. | Re-run/obey the project tooling; match neighbouring code. |
| `poor-naming` | Unclear, misleading, or non-searchable identifiers. | Rename to reveal intent using the language convention. |
| `long-unit` | Function/class does too much or is too long to follow. | Extract smaller single-purpose units. |
| `deep-nesting` | High branching/complexity hurts analysability. | Early returns, guard clauses, decomposition. |
| `duplication` | The same knowledge is expressed in several places. | Extract a shared, well-named abstraction (only when real). |
| `swallowed-error` | Errors caught broadly, ignored, or hidden behind success. | Handle explicitly or propagate; validate at boundaries. |
| `magic-value` | Unexplained literal or hardcoded config. | Named constant or configuration. |
| `dead-code` | Unused, unreachable, or commented-out code. | Delete it. |
| `weak-tests` | Missing tests, happy-path-only, or weakened to pass. | Add edge/failure coverage and a regression test. |
| `over-engineering` | Speculative abstraction or indirection for unused futures. | Inline to the simplest design that meets the requirement. |
| `tight-coupling` | A change ripples across unrelated modules. | Introduce a stable seam/interface; reduce dependencies. |
| `stale-comment` | Comment is wrong, redundant, or explains the obvious. | Fix the why-comment or remove it. |

## Status rubric

| Status | Criteria |
|---|---|
| `ok` | Conforms to conventions; no blocking smells; any minor nits are fixed or deferred with low risk. |
| `warn` | Non-blocking smells remain (e.g., a deferred extract), but the change is maintainable and conventional. |
| `fail` | A blocking smell makes the change hard to maintain, breaks project convention, swallows errors, or ships untested critical behaviour. |
| `n/a` | No project source code changed (docs-only, config-only with no logic, or non-software project). |

Output marker (final summary and `code-quality-reviewer` report):

```text
Code quality: <ok|warn|fail|n/a>; reviewer=<separate|merged|skipped>; signals=<list|none>
```

Every coding/edit-capable and reviewer subagent emits, in its Reporting Template:

```text
Code quality: ok | warn | fail | n/a; signals=<list|none>
```

## Strictness

`code_quality_strictness` is derived in Phase 1.9; it is **not** a second
blocking interview question. It tracks the Build Gate but decouples authoring
craft from verification so "skip the gate" never means "skip clean code":

| Project signal | `code_quality_strictness` |
|---|---|
| `software-dev`, Build Gate `standard` / `strict` / `light` | mirror `build_gate_strictness` |
| `software-dev`, Build Gate `skipped` | `light` (standards still apply, merged into `@reviewer`) unless the user explicitly opts out → `skipped` |
| non-`software-dev` but code-bearing (scripts, IaC, config, notebooks) | `advisory` (standards as guidance; responsibility merged into `@reviewer`) |
| non-`software-dev`, no source code | `n/a` |
| explicit user opt-out | `skipped` with recorded rationale |

- `standard` — apply Rule 0 and the authoring standards; reviewer reports smells.
- `strict` — additionally flag `over-engineering`, `tight-coupling`, and missing
  edge/failure tests as blocking; require the reviewer verdict before done.
- `light` / `advisory` — apply Rule 0 and report `fail`-level smells only;
  responsibility merges into `@reviewer`.

## Role and propagation

| Role | Read/Write | Responsibility (no overlap) |
|---|---|---|
| `implementer` (and edit-capable roles) | edit | Apply Rule 0 and the authoring standards **while writing**; emit `Code quality:` evidence. |
| `code-quality-reviewer` | read-only | The maintainability / convention / code-smell verdict only. Separate role for `standard`/`strict`; merges into `@reviewer` otherwise. |
| `@reviewer` | read-only | Functional correctness, regressions, integration. Owns the code-quality verdict when the reviewer role is merged. |
| `architecture-reviewer` | read-only | Boundaries, patterns, ADR alignment — not line-level craft. |
| `change-bug-hunter` | read-only | Diff-scoped latent bugs / lightweight security sniff — not style/maintainability. |
| `change-validator` | read-only | Evidence aggregator; integrates the `Code quality:` line, never overrides it. |
| `agent-quality-curator` | read-only | Generated agent-system *prose* only — never project source code. |

**Propagation contract (so standards actually reach the code-writing agent):**

1. The host loads the `code-quality` skill before delegating any `code-edit`,
   `bug-fix`, `refactor`, or code review assignment and passes
   `Skills Referenced: code-quality loaded=true` in the delegation packet.
2. Edit-capable and reviewer subagent templates carry a one-line pointer to
   `AGENTS.md` › Code Quality & Maintainability plus the `Code quality:`
   reporting line — not the full standards prose (context-optimization safe).
3. Subagents emit the `Code quality:` marker; `change-validator` aggregates it
   into the Build Gate review evidence.

## AGENTS.md placement

The plugin renders code quality in two places:

1. **`AGENTS.md` › `## Code Quality & Maintainability`** — the compact inline
   standards (Rule 0 + the authoring standards + the output marker) from
   [code-quality-standards snippet](../assets/code-quality-standards.snippet.md).
   `**Audience:** all`. This is the always-on surface every agent reads.
2. **`code-quality` skill** (per runtime, including Codex) — the expanded
   procedure, examples, and the full smell→fix table, loaded on demand before
   implementation.

For non-software-dev projects with no source code, the section renders
`Code quality: n/a — non-software project` and no `code-quality-reviewer` is
emitted.

## Anti-patterns

- Treating the Build Gate (verification) as a substitute for authoring craft, or
  vice versa.
- Importing a generic/personal style instead of the project's configured one
  (Rule 0 violation).
- Pasting the full standards prose into every subagent instead of a one-line
  pointer plus the `Code quality:` marker (context bloat).
- Creating `code-quality-reviewer` with write access, or letting it duplicate
  `@reviewer` / `architecture-reviewer` / `change-bug-hunter` scope.
- Reformatting unrelated lines or churning style on files the task did not touch.
- Confusing `code-quality` (project source) with `content-quality` (agent prose).
- Reporting `Code quality: ok` while smells were skipped without rationale.

## Verification

After generation, the plugin verifier confirms:

1. `AGENTS.md` contains `## Code Quality & Maintainability` with the inline
   standards (Rule 0 + authoring standards) or an `n/a — non-software project`
   rationale.
2. For software-dev with strictness != `skipped`: the `code-quality` skill exists
   at each selected runtime's skills path (including Codex).
3. The roster includes `code-quality-reviewer` (or `code-quality merged into
   reviewer` for `light`/`advisory`/tiny).
4. Edit-capable and reviewer subagent templates carry the `Code quality:`
   reporting marker, and the host packet evidence uses
   `Skills Referenced: code-quality loaded=true`.
5. The Build Gate review gate references this standard so the maintainability
   verdict is part of code review, not a separate silent step.
